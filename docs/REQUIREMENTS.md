# Требования к продукту: Keep-Alive Privacy Lock для macOS

> **Уточнения, принятые при проектировании** (подробнее в [ARCHITECTURE.md](ARCHITECTURE.md)):
>
> - Горячая клавиша только **включает** блокировку. Снять её можно лишь аутентификацией (п. 13.1).
> - «Аварийный выход» (п. 6) реализован как **эскалация в системную блокировку macOS**, а не как комбинация клавиш, которую может нажать посторонний. Крайний случай — принудительная перезагрузка: после неё блокировка не восстанавливается.
> - App Sandbox и Mac App Store (п. 11) несовместимы с полноэкранным киоском и системной блокировкой. Распространение: Developer ID + нотаризация.
> - Блокировка ввода построена на режиме киоска, а не на глобальном event tap, поэтому Accessibility и Input Monitoring не требуются (п. 6).

## 1. Описание продукта

**Keep-Alive Privacy Lock** — приложение для macOS, которое позволяет пользователю временно заблокировать интерактивный доступ к компьютеру, не переводя Mac в сон и не останавливая фоновые процессы.

Приложение предназначено для ситуаций, когда пользователь запускает длительную задачу — например, работу Claude Code, терминального скрипта, сборку проекта, загрузку файлов или другой автоматизированный процесс — и хочет отойти от ноутбука, сохранив конфиденциальность и защиту от постороннего управления.

Приложение не должно получать или хранить пароль пользователя macOS. Для биометрической аутентификации необходимо использовать системный API LocalAuthentication, который поддерживает Touch ID и системную аутентификацию через macOS.

## 2. Цели и ограничения

### Цели

Приложение должно:

- продолжать выполнение фоновых процессов;
- предотвращать управление Mac через клавиатуру, мышь и трекпад;
- защищать открытые приложения от случайных или намеренных действий;
- поддерживать разблокировку через Touch ID;
- не хранить пароль пользователя macOS;
- позволять пользователю видеть безопасный статус выполняемой работы;
- работать предсказуемо при подключённом питании;
- уведомлять пользователя о случаях, когда полноценная защита невозможна.

### Ограничения

Приложение не должно:

- выдавать себя за системный экран входа macOS;
- самостоятельно собирать пароль пользователя;
- обещать абсолютную защиту от владельца устройства, root-доступа, удалённого администрирования или аппаратного вмешательства;
- скрывать от пользователя факт использования Accessibility или Input Monitoring;
- блокировать системные функции таким образом, чтобы пользователь мог потерять доступ к своему компьютеру;
- использовать перехват ввода без явного согласия пользователя.

## 3. Основные режимы

### 3.1. Privacy Lock

Основной режим защиты.

После активации:

- все окна приложений закрываются непрозрачным защитным слоем;
- на экране отображаются только название режима и безопасный статус;
- клавиатура, мышь и трекпад не передают команды приложениям;
- фоновые процессы продолжают работу;
- уведомления и содержимое окон не видны;
- для выхода требуется Touch ID или системная аутентификация.

Пример отображения:

> Mac защищён
> Фоновые задачи продолжают выполняться
> Нажмите Touch ID для разблокировки

Этот режим должен быть рекомендован по умолчанию, поскольку отображение рабочего стола может раскрыть переписку, токены, документы или другую конфиденциальную информацию.

### 3.2. Monitor Mode

Режим наблюдения за выполнением задач.

На экране показывается не весь рабочий стол, а только безопасная панель состояния:

- название задачи;
- время начала;
- прошедшее время;
- текущий этап;
- процент выполнения;
- статус терминального процесса;
- последние безопасные сообщения;
- состояние подключения к сети и питанию.

Пользователь не должен иметь возможности взаимодействовать с исходными приложениями напрямую.

### 3.3. Transparent Mode

Экспериментальный режим, в котором рабочий стол остаётся видимым, но ввод блокируется.

Этот режим должен сопровождаться предупреждением:

> Содержимое экрана остаётся видимым для окружающих. Используйте этот режим только в приватной обстановке.

Transparent Mode не следует считать полноценным режимом конфиденциальности.

## 4. Пользовательские сценарии

### Сценарий A: запуск длительной задачи

1. Пользователь запускает процесс в терминале или другом приложении.
2. Пользователь вызывает Keep-Alive Privacy Lock горячей клавишей или из меню.
3. Приложение проверяет состояние питания и активности.
4. На экране появляется защитный слой.
5. Фоновая задача продолжает выполняться.
6. Пользователь возвращается и проходит аутентификацию через Touch ID.
7. Защитный слой исчезает, а пользователь возвращается к рабочему столу.

### Сценарий B: попытка взаимодействия

1. Mac находится в режиме блокировки.
2. Посторонний человек нажимает клавишу или двигает курсор.
3. Приложение не передаёт действие активному приложению.
4. На экране появляется запрос аутентификации.
5. До успешной аутентификации рабочий стол остаётся недоступным.

### Сценарий C: неудачная аутентификация

1. Пользователь прикладывает неправильный палец или отменяет Touch ID.
2. Защитный слой остаётся активным.
3. Приложение показывает нейтральное сообщение об ошибке.
4. Пользователь может повторить попытку.
5. После заданного количества неудач приложение вводит временную задержку.

## 5. Требования к аутентификации

### Обязательные требования

- Использовать `LocalAuthentication`.
- Поддерживать Touch ID на совместимых Mac.
- Не получать и не сохранять отпечатки пальцев.
- Не сохранять пароль пользователя macOS.
- Не отправлять данные аутентификации в интернет.
- Уметь работать без Touch ID, если устройство его не поддерживает.
- Корректно обрабатывать отмену, блокировку Touch ID и отсутствие биометрии.

Apple предоставляет `LAContext` для проверки личности пользователя через биометрию или системный способ аутентификации; приложение должно использовать именно этот механизм, а не реализовывать собственную проверку пароля macOS.

### Резервный способ

В первой версии резервным способом может быть системная аутентификация macOS через `deviceOwnerAuthentication`, если это поддерживается выбранной политикой.

Необходимо отдельно проверить пользовательский сценарий на конкретных версиях macOS, потому что приложение не должно самостоятельно рисовать форму для ввода основного пароля компьютера.

## 6. Требования к блокировке ввода

Во время активной защиты приложение должно предотвращать:

- ввод текста;
- клики мышью;
- нажатия кнопок трекпада;
- переключение приложений;
- открытие контекстных меню;
- случайное закрытие защитного слоя;
- перетаскивание окон;
- запуск команд через обычные горячие клавиши;
- доступ к рабочему столу через Mission Control и Spaces, насколько это возможно средствами macOS.

Для глобального наблюдения или фильтрации событий могут потребоваться Accessibility и Input Monitoring. Такой доступ должен запрашиваться только после объяснения пользователю, зачем он нужен. Apple предоставляет для подобных сценариев Accessibility API и event tap-механизмы, но их использование требует учитывать системные разрешения macOS.

Приложение должно иметь функцию аварийного выхода, например:

- удержание определённой комбинации клавиш в течение нескольких секунд;
- системное завершение процесса;
- отдельная команда из меню приложения;
- отключение через безопасный режим macOS.

Нельзя создавать необратимую блокировку устройства.

## 7. Требования к окну защиты

Защитный слой должен:

- покрывать все активные мониторы;
- работать при нескольких рабочих столах;
- корректно обрабатывать подключение и отключение внешнего монитора;
- оставаться поверх обычных окон;
- не позволять открыть другое приложение поверх него;
- поддерживать полноэкранный режим;
- корректно работать с вырезом камеры и меню macOS;
- не показывать содержимое предыдущего окна при появлении;
- очищать чувствительные данные из памяти интерфейса при блокировке.

Для работы с Spaces, Mission Control и полноэкранными окнами потребуется использовать параметры `NSWindow.CollectionBehavior`; Apple документирует эти настройки как механизм управления поведением окон в Spaces, Stage Manager и полноэкранных режимах.

Важно зафиксировать в требованиях: обычное приложение macOS не может гарантировать такой же уровень защиты, как системный экран блокировки Apple. Поэтому продукт должен явно показывать пользователю границы своей защиты.

## 8. Управление питанием

Приложение должно:

- предотвращать автоматический сон во время активной задачи;
- различать работу от батареи и от адаптера;
- предупреждать о высоком расходе энергии;
- показывать оставшийся заряд;
- предлагать автоматически перейти в безопасный режим при низком заряде;
- не препятствовать намеренному закрытию крышки;
- восстанавливать исходные настройки питания после завершения режима;
- корректно обрабатывать отключение зарядного устройства.

При этом приложение не должно без предупреждения оставлять Mac включённым на батарее на длительное время.

Желательное поведение:

- от сети: разрешить выполнение задачи до завершения;
- от батареи: показывать предупреждение;
- при заряде ниже заданного порога: предложить остановить задачу или перевести Mac в обычную блокировку;
- при закрытии крышки: использовать стандартное поведение macOS, если пользователь явно не включил специальный режим.

Apple предоставляет системные настройки для контроля сна, выключения дисплея и поведения Mac при питании от батареи или адаптера.

## 9. Отображаемая информация

В Privacy Lock на экране разрешается показывать только:

- состояние блокировки;
- время блокировки;
- имя выбранной задачи;
- длительность выполнения;
- общий статус: «выполняется», «завершено», «ошибка»;
- безопасное пользовательское сообщение;
- состояние питания;
- состояние сетевого подключения;
- кнопку или подсказку для разблокировки.

Не разрешается показывать:

- содержимое чатов;
- текст команд;
- API-ключи;
- пароли;
- полный вывод терминала;
- имена конфиденциальных файлов;
- уведомления сторонних приложений;
- содержимое окон рабочего стола.

## 10. Уведомления и завершение задачи

При завершении фоновой задачи приложение должно:

- не снимать блокировку автоматически;
- показывать безопасный статус «Задача завершена»;
- показывать безопасный статус ошибки без конфиденциального текста;
- опционально воспроизводить звуковой сигнал;
- опционально отправлять уведомление после разблокировки;
- сохранять подробный результат только в самом рабочем приложении или выбранном пользователем журнале.

Если процесс завершился аварийно, приложение не должно автоматически открывать терминал или выводить чувствительный лог на экран.

## 11. Безопасность

Приложение должно:

- использовать App Sandbox, если это совместимо с требуемыми функциями;
- подписываться и распространяться через Developer ID или Mac App Store;
- защищать настройки от изменения во время активной блокировки;
- хранить секреты только в Keychain;
- не передавать телеметрию без согласия;
- вести локальный журнал событий без содержимого пользовательских данных;
- очищать чувствительные данные из интерфейса перед блокировкой;
- не изменять системные файлы;
- не устанавливать скрытые фоновые компоненты;
- ясно показывать наличие разрешений Accessibility, Input Monitoring и Screen Recording, если они требуются.

Для чувствительных ключей и настроек можно использовать Keychain с дополнительной защитой через LocalAuthentication. Apple отдельно документирует использование Touch ID для доступа к защищённым элементам Keychain.

## 12. Архитектура первой версии

Рекомендуемый состав MVP:

- основное приложение на Swift и SwiftUI;
- AppKit-слой для полноэкранного защитного окна;
- `LocalAuthentication` для Touch ID;
- отдельный сервис контроля состояния питания;
- модуль отслеживания подключённых мониторов;
- контроллер режимов `Privacy`, `Monitor`, `Transparent`;
- минимальный локальный журнал событий;
- настройки горячей клавиши и поведения при низком заряде;
- интеграция с процессами через пользовательские статусы, а не через чтение всего экрана.

Для первой версии не нужно пытаться управлять любым процессом автоматически. Лучше дать пользователю возможность вручную указать:

- название задачи;
- безопасное описание;
- ожидаемую длительность;
- команду или процесс для мониторинга;
- способ определения завершения.

## 13. MVP

В минимальную первую версию следует включить:

1. Активацию и деактивацию через горячую клавишу.
2. Непрозрачный Privacy Lock.
3. Полноэкранный защитный слой на всех мониторах.
4. Блокировку обычного ввода.
5. Разблокировку через Touch ID или системную аутентификацию.
6. Предотвращение сна во время активного режима.
7. Индикацию питания и заряда батареи.
8. Безопасный статус выполнения.
9. Настройку автоматической блокировки.
10. Аварийный выход.
11. Явные объяснения всех запрашиваемых разрешений.
12. Восстановление системных настроек после выхода.

## 14. Критерии приёмки

Функция считается реализованной, если:

- после активации пользователь не может случайно открыть, изменить или закрыть рабочее приложение;
- защитный слой покрывает все подключённые мониторы;
- Touch ID корректно разблокирует режим;
- при отсутствии Touch ID доступен системный резервный способ;
- пароль macOS не сохраняется приложением;
- фоновый процесс продолжает работу;
- Mac не засыпает вопреки выбранным настройкам;
- после завершения режима настройки питания возвращаются к исходным значениям;
- закрытие и повторное открытие крышки обрабатываются предсказуемо;
- приложение не раскрывает текст терминала, переписки или уведомлений;
- пользователь может аварийно выйти из режима;
- после перезагрузки Mac приложение не создаёт постоянную блокировку;
- приложение сообщает, если невозможно гарантировать перехват всех способов ввода.

## 15. Главный продуктовый принцип

Ключевое обещание продукта следует сформулировать так:

> «Ваш Mac продолжает работать, но его текущая сессия недоступна для управления, пока вы не подтвердите личность».

При этом нельзя обещать: «никто не сможет получить доступ к Mac». Более точная формулировка:

> «Приложение защищает активную пользовательскую сессию от обычного физического доступа, сохраняя работу фоновых задач. Для максимальной защиты используйте стандартную блокировку macOS и не оставляйте конфиденциальные данные открытыми на экране».
